# LoveBud Gallery 이미지 자산 워크플로

## 1. 목적

이 문서는 LoveBud Gallery에 이미지를 추가·수정·대체·보관·공개 중단하는 절차를 정의합니다.

## 2. 역할

### 자산 제공자

- 캡처·디자인·슬라이드 원본 제공
- 출처와 화면 상태 설명
- 실제 개인정보가 없음을 확인

### 제품 검토자

- 현재 제품·개발 중·컨셉·과거 화면 판정
- 제목·설명·기능 영역 확인
- 최신 화면과 대체 관계 확인

### 공개 검토자

- 공개 저장소와 공개 배포 가능 여부 확인
- 미출시 기능·제3자 권리·개인정보 검토

### 개발 검토자

- 파일 형식·해상도·용량 확인
- 매니페스트·썸네일·최적화본 생성
- 모바일·접근성·배포 검증

역할은 한 사람이 겸할 수 있지만 검토 항목은 생략하지 않습니다.

## 3. 신규 자산 추가 절차

### 3.1 원본 준비

- 화면에 실제 개인정보가 없는지 확인
- 불필요한 브라우저 UI·개발자 도구·알림 제거
- 제품 화면의 상태와 출처 커밋 기록
- 원본을 `assets/originals/`에 저장

### 3.2 메타데이터 작성

다음을 기록합니다.

- 고유 ID
- title
- description
- alt
- category
- platform
- status
- assetType
- version 또는 capturedAt
- sourceRepository와 sourceRef
- publicApproval
- rightsStatus
- order

### 3.3 파일 생성

- 웹 표시용 WebP·AVIF 생성
- 썸네일 생성
- width·height 기록
- 원본·web·thumbnail 관계 확인

### 3.4 검증

- 모든 파일 존재
- 중복 ID 없음
- 파일 크기 예산 준수
- 공개 승인 상태 확인
- 실제 브라우저에서 표시
- 모바일에서 잘림 없음
- 의미 있는 alt 확인

### 3.5 PR

PR에는 다음을 포함합니다.

- 추가·교체하는 자산 목록
- 자산 상태
- 공개 승인 근거
- 출처 ref
- 최적화 전후 크기
- 갤러리 화면 캡처
- 검증 결과

## 4. 기존 자산 수정

제목·설명·상태만 바뀌면 매니페스트를 수정합니다.

이미지 픽셀이 바뀌면 다음을 수행합니다.

1. 원본 교체 또는 새 버전 추가
2. web·thumbnail 재생성
3. version 또는 capturedAt 갱신
4. 변경 이유 기록
5. 이전 자산 보관 여부 결정

파일을 덮어써서 과거 화면의 의미를 잃지 않도록 합니다.

## 5. 최신 화면으로 대체

과거 화면은 삭제보다 archive가 기본입니다.

```json
{
  "id": "home-v1",
  "status": "archived",
  "supersededBy": "home-v2"
}
```

최신 화면에는 필요 시 다음을 기록합니다.

```json
{
  "id": "home-v2",
  "status": "current",
  "supersedes": "home-v1"
}
```

## 6. 컨셉·AI 생성 이미지

- `assetType: generated-concept`
- `status: concept` 또는 `presentation`
- 설명에 실제 제품 화면이 아님을 표시
- 생성 도구와 생성·편집 여부를 기록할 수 있음
- 실제 제품 캡처 필터에 포함하지 않음

## 7. 발표용 슬라이드

발표용 이미지는 다음을 구분합니다.

- 실제 화면을 그대로 사용한 슬라이드
- 텍스트·프레임을 추가한 가공 이미지
- 제품 흐름을 설명하는 합성 이미지
- AI 생성 배경·컨셉 이미지

`presentation` category와 `presentation-slide` assetType을 사용합니다.

## 8. 공개 중단 절차

다음 상황에서는 즉시 노출을 중단합니다.

- 개인정보 발견
- 미출시 기능 공개 철회
- 잘못된 제품 정보
- 제3자 권리 문제
- 회사·사용자 요청

절차:

1. 매니페스트에서 공개 대상 제외
2. `dist/` 재생성
3. 배포 반영 확인
4. 원인과 처리 결과 기록
5. 저장소 이력까지 제거해야 하는지 별도 판단

## 9. 파일 삭제

다음 조건을 모두 확인한 후 삭제합니다.

- 다른 자산이 참조하지 않음
- 최신·대체 관계가 정리됨
- 발표자료나 외부 링크에서 사용하지 않음
- 원본 보관 필요가 없음
- 배포본에서 제거됨

삭제보다 archive 이동이 적절한지 먼저 판단합니다.

## 10. 카테고리 변경

카테고리는 파일명을 바꾸지 않고 매니페스트에서 변경합니다.

카테고리 enum을 변경할 때는 다음을 함께 검토합니다.

- 필터 UI
- 기존 deep link
- 정렬
- README·정책 문서
- 검색·통계

## 11. 일괄 자산 추가

대량 캡처는 먼저 인벤토리 PR로 분리할 수 있습니다.

1. 원본 추가
2. 매니페스트 초안 생성
3. 상태·공개 승인 검토
4. 최적화본 생성
5. UI 노출 PR

한 PR에 수십 개 원본과 UI 구조 변경을 동시에 넣지 않는 것을 권장합니다.

## 12. 자산 이름 변경

파일명 변경 시 다음을 확인합니다.

- 매니페스트 file·webFile·thumbnail
- Git case-sensitive 경로
- 배포 캐시
- deep link가 ID 기반인지 여부
- 외부에서 직접 파일 URL을 사용했는지 여부

자산 ID는 파일명이 바뀌어도 유지하는 것이 원칙입니다.
